# Implementation plan — v4: CLI vs MCP delegation benchmark

Goal: extend the verified benchmark to a v4 cohort comparing CLI vs MCP interfaces at full vs certificate output modes, without assuming any arm is superior. The v1–v3 cohorts are complete; their protocols, records and reports live in `docs/`, `reports/`, `main*/` and `pilot/` and are never pooled with v4 (`README.md:7`).

1. **Planned (v4): CLI vs MCP delegation cohort — adds MCP arms.** Status: design draft, awaiting owner approval; no implementation code yet. Keeps the pasted prompt's phases and operating rules but replaces its arm grid (see review notes below). Separate v4 cohort — never pooled with v1/v2/v3/pilot (`README.md:7`, `docs/main-run.md:59`).

   Arms (new v4 labels; frozen v1/v3 letters A–D mean direct / raw-tool / raw-verifier / certificate — `docs/protocol.md:24`, `src/orchestrator.rs:59-65,534-599` — and are not reused):

   | v4 label | interface | output mode | definition |
   |---|---|---|---|
   | `direct` | none | full artifact | model writes artifact via `put`; `submit` is a no-op ack (`orchestrator.rs:445-508`) |
   | `cli-full` | CLI `submit(commands)` | full | sandboxed allowlisted argv; feedback = bounded raw tool output + raw verifier details, capped at `feedback_bytes` |
   | `cli-cert` | CLI | compact | same execution; feedback = certificate only (`Mode::Certificate`, ≤96 B; `certificates.rs:3,30-44`, `feedback.rs:33-42`) |
   | `mcp-full` | MCP tools (stdio JSON-RPC) | full | as `cli-full`, tool results carry the bounded raw payloads |
   | `mcp-cert` | MCP tools | compact | as `cli-cert`; tool result = certificate string only |

   Contrasts: `cli-full`–`cli-cert` and `mcp-full`–`mcp-cert` (compression), `cli-full`–`mcp-full` and `cli-cert`–`mcp-cert` (interface at matched output mode), `direct` vs each delegation arm. Interface overhead := total provider-token difference at matched output mode, including JSON-RPC framing and `tools/list` schema bytes (captured via `schema_bytes`, `orchestrator.rs:186`).

   Substeps (each gated by `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, `cargo test --locked` — `README.md:36-40`):
   - 1.0 Owner answers the open decisions below; freeze `docs/protocol-v4.md` + `configs/experiment-v4.json` before any live run.
   - 1.1 Fix the P2 defects found in review, with regression tests: stale verifier PASS on mutating execution error (`src/orchestrator.rs:525` vs reset at `:547-548`), error-classification mismatch (`src/executor.rs:534` vs `src/collect.rs:75-80`), forgeable quota substring scan (`src/pilot.rs:213-227,526-545`; `src/collect.rs:226-239`), non-atomic JSONL append (`src/pilot.rs:144-153`), connector credential hygiene — header-value validation and temp-file cleanup on all paths (`src/luna_connector.rs:263-345`).
   - 1.2 Instrumentation: component-wise usage (fresh input / cache-read / cache-write / output), `tools/list` schema bytes for MCP arms, tool-result bytes, per-run delegation-compliance flag (agents ignore assigned interfaces — Alier et al., arXiv:2608.08654), cost per verified success at assumed list prices (provider pricing is null).
   - 1.3 Minimal MCP server: hidden `mcp-server` subcommand (`main.rs:59-61` pattern), local stdio subprocess at config-supplied absolute path reusing `Connector` spawn/drain/timeout/kill (`model_adapter.rs:75-165`); surface = the 6-variant `Action` enum (`read`/`put`/`remove`/`mkdir`/`submit`/`finish`; `model_adapter.rs:205-226`), one tool per action; operator subcommands stay CLI-only; framework `rmcp` with hand-rolled JSON-RPC fallback. All tool execution goes through the same `execute_routed` sandbox (`executor.rs:601-724`); the server never executes model argv itself.
   - 1.4 Arm wiring: five v4 labels in the orchestrator, MCP `tool_calls`→`Action` translation, feedback modes per arm, analysis pairs extended (`analysis.rs:619,725` pattern). Check: all five arms through the real sandbox against a provider double (`tests/pilot_cli.rs` pattern).
   - 1.5 Pilot v4: 2 sandbox-proved tasks × 5 arms × 5 reps = 50 live runs. Acceptance: 50/50 records with 100% `api_reported` usage (a run without provider-reported usage is `usage_error`, kept in denominators, excluded from token contrasts — `orchestrator.rs:234-238`; this is the fix for v3's 26/576 unknown usage), byte-identical report regeneration, owner review before any expansion.
   - 1.6 Main v4: 23 sandbox-proved tasks (12 filesystem + 11 valid-text, `README.md:11`) × 5 arms × 3 reps = 345 cells, protocol frozen pre-execution, sharded, no pooling. The 24 sorting/aggregation cases and the invalid-UTF-8 case stay out until the native-only cutover completes (`README.md:11-13`).
   - 1.7 Analysis + `main-v4-report/`; each hypothesis independently; limitations (single model, assumed prices, 23/48 task coverage); null results reported as-is.

   Acceptance for v4 overall: gates green at every substep; 100% provider-reported usage in the pilot; success = hidden oracle PASS only (`orchestrator.rs:322-332`); 5 pp one-sided non-inferiority margin frozen pre-execution (`docs/protocol.md:42`); task-cluster bootstrap; no imputation; reports regenerate byte-identical from JSONL; historical cohorts and `dataset/` untouched.

   Exclusions: no remote HTTP/MCPB, no widgets, no elicitation, no search+execute pattern, no wrapping operator subcommands as tools, no new provider abstraction (`ModelAdapter`/`Connector` config-swap already is it), no multi-provider, no new task families.

   Evidence and rationale (from the 2026-11-25 groundwork review; details in session agents): v3 success direct 16.7% vs delegation 70.1–73.6% with D−A non-inferiority exploratory-supported, but H1 token reduction not established (26/576 unknown usage); v1/v3 CLI arms ran model-written Python, so they are not prior evidence for native-utility claims (`README.md:9`); literature (45 sources) supports delegation's correctness benefit (PAL arXiv:2211.10435, PoT arXiv:2211.12588, ToolHop arXiv:2501.02506), shows tokens ≠ cost (Tran, aclanthology.org/2026.realm-1.24.pdf; Weinberger & Hozez arXiv:2607.12161, r=0.15), and shows the CLI-vs-MCP effect is small and harness/model-dependent (MICA arXiv:2610.34298; Scale Labs labs.scale.com/blog/mcp-vs-cli; Alier et al. arXiv:2608.08654; Potapov 1.13× matched) — no study crosses interface × output mode against a no-tool baseline on oracle-scored exact transformations, which is the gap v4 fills; compaction can backfire (truncation 98.6%→47.2% success, Tran), so the certificate arms rest on verifier fidelity.

   Open decisions for the owner (block 1.0): (1) full prompt text — Phases 0–4 and the hypothesis list were not in the pasted fragment; (2) confirm v4 as a separate cohort with the labels above; (3) does `direct` get a compact variant, and keep or drop the raw-verifier ablation?; (4) pilot size 50?; (5) full-output definition = raw tool + raw verifier bounded by `feedback_bytes`; (6) reuse the 5 pp one-sided margin, secondary contrasts exploratory/unadjusted; (7) confirm 1.1 lands before 1.3.

Plan review: v4 reuses the sandbox, verifier/oracle, certificates, replay/connector adapter, scheduler and analysis core; new code is ≈300–400 lines (`main.rs` +~5, new `mcp_server.rs` ~150–250, MCP client ~100, `orchestrator.rs` ~50). Local stdio subprocess (not in-process, not remote) preserves the trust rule that model output never supplies the server path (`model_adapter.rs:83-91`).
